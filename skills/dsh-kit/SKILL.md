# dsh-kit

`dsh-kit` generates a DSH plugin with the layout, build, type checking, tests and verification already wired.
Do not rebuild that layer by hand.

## 1. Generate

```bash
pnpm create dsh-kit my-plugin
cd my-plugin
pnpm install
pnpm verify
```

For a non-interactive run, add `--yes` and `--author`. Keep pnpm as the primary package manager; npm is supported.

## 2. Implement

- `src/host/index.ts` is the Host entry; keep data and transport separate.
- `src/client/index.tsx` is the browser entry. The ModuleLoader wrapper is generated by `tsdown.config.ts`;
  never hand-write it.
- Register UI through documented slots (`sidebar.panellist`, `main`, `conversation.input.left`,
  `conversation.input.dock`, `shell.overlay`).
- If a composer draft is involved, saving must not clear it. Clearing is a separate, labelled action.
- Use only documented DSH APIs. Add tests for the store and for client registration.

## 3. Verify

```bash
pnpm verify
dsh plugin --profile <profile> add link:$PWD
```

The real proof is: the packed artifact installs, DSH boots, the entry appears, the UI works, and the console has
no errors. A green unit test suite alone is not enough.

## 4. Debug

```bash
pnpm test
pnpm build
dsh --profile <profile> --dump-config | grep -A2 "id: my-plugin"
```

Rebuild and restart DSH after client changes. Use browser DevTools for the client and the Host log for route or
tool registration failures.

## 5. Document and release

- Every plugin gets its own docs site; do not park plugin docs under the dsh-kit site.
- Read `PUBLISHING.md` before the first release. `main` is protected; releases are tag-driven and publish with
  provenance.
- To join the curated list, read `CURATION.md` and open a Plugin application issue.

## Guardrails

- No new runtime dependencies in the template.
- No undocumented DSH APIs.
- No secrets, private paths or third-party copyright in generated output.
- Do not add a plugin when a skill or instruction file is enough.
